ROS 2 bin-picking stack — architecture

How the repository is organised, which node does what, and how a camera frame turns into a robot motion. Read top to bottom the first time; the second half is a reference for every node, topic, service, action and message.

1. Overview in 60 seconds

The system picks cans out of a bin, one layer at a time, with a Yaskawa Motoman cobot guided by an Orbbec Astra RGB-D camera. Three processes are involved and only one of them lives in this repository:

ProcessWhere it runsLanguageJob
Astra ZMQ streamer external Host PC, next to the USB camera (separate codebase) C (Orbbec Astra SDK + libzmq) Opens the camera, aligns depth to color, publishes both streams over ZMQ PUB on ports 5550/5551 and writes the camera intrinsics JSON.
cobot-ros container PythonC++ Docker on the host PC (docker compose up) ROS 2 Humble, rmw_cyclonedds Everything in ros2_ws/: 8 nodes from one launch file — camera bridge, ONNX detection, localization/calibration math, task orchestration, pick choreography, the YMConnect hardware driver, the web UI and a health monitor.
YRC1000 controller hardware Robot cell LAN (192.168.1.31) Yaskawa firmware Owns the arm: servos, trajectory execution, IO bits for the gripper and sensors, alarms. Driven exclusively by cobot_control through the vendored libYMConnect.so.

Data flows strictly left to right: pixels (camera_node → detector_node) become millimetres in the robot base frame (localization_node) become an ordered list of pick goals (task_manager) become a sequence of moves and IO writes (cobot_operation) become YMConnect calls (cobot_control). Every node also emits a heartbeat, and the web node mirrors the whole state to a browser.

Two side channels run alongside the main pipeline:

  • Observation — web_node subscribes to the images, detections, targets, task and health topics, JPEG-encodes the frames and pushes everything to the browser over one WebSocket; browser commands come back as Trigger/StartWorkflow service calls.
  • Health — every node publishes a Heartbeat every 2 s; health_monitor folds them into a latched /health/summary that task_manager uses to compute capability and web_node shows on the dashboard.

4. One pick_layer run, end to end

The default workflow. Triggered by the UI's Start button (/task/start) or /task/start_workflow {workflow: "pick_layer"}.

  1. browser → web_node: WebSocket {receiver:"COBOT", command:"start"}. web_node calls std_srvs/Trigger /task/start.
  2. task_manager: checks /task/system_state capability is OPERATE (robot fresh, connected, servo on, not alarming, camera OK, calibrated, depth fresh, detector OK). Publishes TaskStatus SCANNING. Sends Scan.Goal{model_id: scan_model_id} to /vision/scan.
  3. localization_node: rejects if not calibrated / no depth / detector missing. Otherwise forwards Detect.Goal{model_id} to /vision/detect (feedback detecting).
  4. detector_node: takes its latest /camera/color/image_raw, runs the ONNX session for that model (default cans, OBB head), returns ObbDetectionArray with pixel centres, corners and angles; also publishes it on /vision/detections_px for the UI overlay.
  5. localization_node (feedback localizing): for each detection samples the median depth in a depth_sample_window_px window from the depth ring buffer, applies xyz = M · [u·d, v·d, d, 1], converts the OBB angle to a robot rz, drops entries with no depth, sorts into a snake along pathing_row_axis, publishes /vision/targets and returns TargetArray.
  6. task_manager: for each Target publishes TaskStatus PICKING i/N and sends PickCan.Goal{target} to /cobot/pick_can (budget 300 s). /task/stop cancels the in-flight goal natively.
  7. cobot_operation: goal accepted only when /cobot/status == IDLE. Phases (each reported as feedback): check (teach point from trajectories.json) → approach (above target, then linear descend with the descend profile to pick_tip_z_mm) → grip (/cobot/set_output_bit gripper=true) → lift (back up, back to check, assert existance_check==true from /cobot/state, read divot_check/right_complete/left_complete) → place (2-pose teach trajectory: left/right, _flip variant when the divot sensor says so; gripper off; assert sensor again).
  8. cobot_control: each MoveToPose is rejected unless connected, servo on, not alarming, control mode ≠ TEACH and not busy. It runs an IK reachability check, AddPointToTrajectory (joint or linear, speed / accel / decel / accuracy from the named motion profile), MotionStart, then polls GetMotionTargetProgress until reached or motion_timeout_s. Meanwhile the 10 Hz poll keeps /cobot/state current so cobot_operation can read sensors.
  9. task_manager: after a successful pick calls /vision/verify_target (a second depth read at the target; present==false means the can is gone) and publishes a PickEvent per can. The verdict is informational — it does not yet trigger a rescan.
  10. task_manager: publishes /task/layer_report and TaskStatus IDLE. web_node forwards every status, pick event and report to the browser as it happens.
Calibration workflows follow the same pattern but task_manager drives /cobot/move_to_pose directly through a grid of poses (calibration_x/y_range_mm, calibration_z_levels_mm) and calls /vision/calibration_begin → N × /vision/calibration_sample{x,y,z} → /vision/calibration_compute. localization_node finds the red marker on the tool (red_dot model, or — currently — a manual click relayed from the web UI on /vision/manual_dot_click), pairs the camera measurement with the commanded TCP + marker_offset_mm, and fits the 3×4 matrix written to calibration.yaml. With auto_calibrate_on_startup: true a small startup_calibration grid runs at boot — the arm moves at launch.

6. Node reference

All eight nodes are started by ros2_ws/src/cobot_bringup/launch/robot.launch.py with respawn=True, no namespaces and no remappings, all reading config/cobot_params.yaml. Launch arguments camera, vision, cobot, tasks, web, health (all default true) switch groups off for partial bring-up. Every node also publishes /health/heartbeat (Heartbeat, every heartbeat_period_s = 2 s) — omitted from the tables below.

camera_node

Pythonpackage cobot_camera · cobot_camera/camera_node.py, camera_streamer.py

The only bridge between the outside camera and ROS. CameraStream runs two background ZMQ SUB threads (color, depth), each keeping only the newest frame (RCVHWM=2, drain with NOBLOCK, deliberately no ZMQ_CONFLATE because libzmq aborts on multipart). A timer at publish_rate_hz republishes whichever cached frame is new. It never decodes, resizes or aligns anything — depth arrives already aligned to color and is forwarded as-is (16SC1, mm). It also relays the streamer's intrinsics file as a latched CameraInfo (re-read only when the file mtime changes) and can dump a color/depth PNG pair to capture_dir for building training sets.

detector_node

C++package cobot_detector · src/detector_node.cpp, onnx_detector.cpp, model_registry.cpp, letterbox.cpp, postprocess.cpp

Perception in pixel space only — "no geometry, no millimetres". Holds one ONNX Runtime session per model id listed in models.yaml (runtime: and calibration: sections; preload loads some at start, the rest lazily). Input geometry is read from the graph ([1,3,H,W]), and each model is cross-checked against the manifest.yaml next to the .onnx so a mislabelled export fails at load rather than at pick time. Supports three head layouts: raw ([1, 4+nc(+1), N], NMS in node), end2end ([1, max_det, 6|7], NMS in graph — the cans OBB model) and seg (YOLOE, boxes only). Each accepted Detect goal runs on its own thread; only one may be in flight. The pure C++ core (detector_core) has gtests that run during the Docker build.

localization_node

Pythonpackage cobot_vision · cobot_vision/localization_node.py, calibration.py, pathing.py, rotation.py

Where pixels become robot coordinates. Keeps a ring buffer of the last depth_buffer_size depth frames and the fitted camera→robot transform from calibration.yaml ([X,Y,Z]ᵀ = M · [u·d, v·d, d, 1]ᵀ, 3×4, mm). A Scan goal fans out to /vision/detect, then for every detection: median depth in a window around the centre, matrix multiply, OBB angle → rz in robot convention, snake ordering along pathing_row_axis. The same depth machinery backs verify_target (is the can still there?) and get_layer_height. It also owns the calibration math (task_manager owns the sequencing): begin clears samples, sample{x,y,z} locates the tool marker (red_dot model or manual click) and pairs it with the commanded TCP + marker_offset_mm, compute fits either a full 12-parameter least squares (require_intrinsics: false) or a Kabsch extrinsic fit with SDK intrinsics, rejects fits above calibration_max_rms_mm, and persists the result.

task_manager

Pythonpackage cobot_tasks · task_manager_node.py, context.py, system_state.py, workflows/{base,pick_layer,calibration}.py

The orchestrator. Workflows are plain Python classes that declare the clients and parameters they need and a run(ctx) that calls them in order through a WorkflowContext (no rclpy in workflow code). The node creates one client per declared ClientSpec, runs a single workflow at a time, publishes progress, and implements stop by cancelling the in-flight goal. Once a second it re-derives SystemState: robot side from /cobot/state freshness, vision side from /health/summary (camera OK, calibrated, depth fresh, detector OK) — and lists which workflows are ready given the resulting capability bitmask (SEE=1, MOVE=2, OPERATE=3). The UI's buttons are literally rendered from /task/workflows.

cobot_operation

Pythonpackage cobot_operation · operation_node.py, primitives.py, choreography.py, geometry.py, report.py, setup_config.py

The pick-and-place choreography, kept in Python so it is easy to change. It knows nothing about YMConnect: its primitives are move(pose, profile) (a MoveToPose goal), set_output(name, value) (a SetOutputBit call) and wait_for_sensor(name, expected) (watch /cobot/state until the named input matches). choreography.py sequences them through check → approach → grip → lift → place using the active tool profile from cobot_setup.yaml (tip_offset_mm, pick_tip_z_mm, approach_tip_z_mm, descend_profile) and the taught place trajectories in trajectories.json (check, left, right, left_flip, right_flip). The result carries a JobResult per primitive and a SensorAssert per check so the UI can show exactly where a pick failed.

cobot_control

C++package cobot_control · src/cobot_control_node.cpp, motoman_robot.cpp, setup_config.cpp, third_party/YMConnect/

The hardware driver and the only process that holds a YMConnect session to the YRC1000. On start it OpenConnection(robot_ip), turns servos on and clears any stale trajectory, then retries every connect_retry_period_s if the link drops. A timer polls the controller every poll_period_s (10 Hz): ReadState (servo / running / hold / alarm / error / control mode), one ReadByte per IO group covering every named sensor and output from cobot_setup.yaml, ReadPositionData for the TCP pose, and GetActiveAlarms when alarming — all folded into one CobotState message that everyone else reads instead of touching the controller. Motion is trajectory-point based, not INFORM-job based: a MoveToPose resolves a named motion profile, optionally checks reachability through the kinematics API, calls AddPointToTrajectory + MotionStart, and reports progress until reached, stopped, alarmed or timed out. Pause/resume is MotionStop(false)/MotionStart() (or the HOLD signal when pause_uses_hold). Status transitions can be mirrored on the teach pendant.

web_node

Pythonpackage cobot_web · web_node.py, templates/index.html, static/app.js, static/commands.js

Operator dashboard. A FastAPI app served by uvicorn on the main thread with rclpy spinning on a background thread. It subscribes to nearly everything, JPEG-encodes the latest color and (min-max normalised) depth frames at web_stream_hz, and pushes JSON messages over a single WebSocket (/ws); on connect it replays the latched state so a fresh tab is immediately correct. health_monitor

Pythonpackage cobot_health · health_monitor_node.py, heartbeat.py (the HeartbeatPublisher helper every Python node embeds; the C++ nodes re-implement it)

Collects every Heartbeat and publishes one latched HealthSummary per second. A node in expected_nodes that has never reported is UNKNOWN; one whose last heartbeat is older than stale_factor × period_s is STALE; otherwise its own level (OK / WARN / ERROR) and metrics are passed through. The summary's level is the worst across nodes, with STALE/UNKNOWN counting as ERROR. task_manager reads it to decide whether the vision side is usable; web_node shows it as the health panel.

Subscribes

7. External components

7.1 Astra ZMQ streamer (host side, C + Orbbec Astra SDK)

A small standalone C program that lives outside this repository (its ancestors are the Astra SDK ColorReaderPoll / DepthReaderPoll C-API samples vendored under legacy/cpp/third_party/AstraSDK/samples/; the SDK manual is docs/dependancies/orbbec_devices/AstraSDK_Doc_en.chm). It is the only code that touches the camera: the container never opens USB, which keeps the Docker image portable and lets the camera driver be restarted independently. The contract camera_node expects is:

ItemContract
SocketsTwo ZMQ PUB sockets, bind tcp://*:5550 (color) and tcp://*:5551 (depth). The container is the SUB/client and connects out to host.docker.internal; no ports are published for it in compose.
Latency rulezmq_setsockopt(ZMQ_SNDHWM, 1) before bind, so a slow subscriber gets the newest frame instead of a growing queue.
FramingMultipart: part 1 = header, part 2 = payload (SNDMORE). camera_node also accepts header+payload in one message and the legacy two-message form.
HeaderPacked little-endian struct "<BIHHBI" = 12 bytes: uint8 stream_type (0 color, else depth), uint32 frame_index, uint16 width, uint16 height, uint8 channels, uint32 payload_size. Payload length must equal payload_size or the frame is dropped.
Color payloaduint8 [h][w][channels], RGB order, 640×480 — republished as rgb8.
Depth payloadint16 [h][w] millimetres, registered/aligned to the color image so pixel (u,v) is the same point in both streams; 0 = no reading. Republished unchanged as 16SC1.
IntrinsicsWrites vision_workspace/operation/camera_intrinsics.json = {"fx","fy","cx","cy","width":640,"height":480} for the color stream, read by camera_node into /camera/color/camera_info. Note: this camera's SDK reports fx/fy that disagree with measured data, which is why calibration ships with require_intrinsics: false.

A minimal publish loop, for orientation:

// per frame, after astra_reader_get_next_frame / astra_frame_get_colorframe|depthframe
hdr.stream_type  = 0 /* color */ or 1 /* depth */;
hdr.frame_index  = frame_index++;
hdr.width = 640; hdr.height = 480;
hdr.channels     = 3 /* color */ or 1 /* depth */;
hdr.payload_size = width * height * channels * bytes_per_sample;   // 921600 color, 614400 depth
zmq_send(pub, &hdr, 12, ZMQ_SNDMORE);
zmq_send(pub, pixels, hdr.payload_size, 0);

7.2 Yaskawa YRC1000 controller + Motoman cobot

The robot controller sits on the cell LAN at 192.168.1.31 (parameter cobot_control.robot_ip). It is driven through Yaskawa's YMConnect SDK (vendored libYMConnect.so + YMConnect.h in ros2_ws/src/cobot_control/third_party/YMConnect/), which speaks the controller's high-speed Ethernet server protocol. Only cobot_control links against it; everything else in the graph sees the robot as /cobot/state, /cobot/status, the MoveToPose action and the /cobot/* services.

9. Runtime, configuration & health

Docker

docker/Dockerfile has two stages. builder (ros:humble) installs apt/pip deps and ONNX Runtime 1.19.2 to /opt/onnxruntime, runs rosdep against the ten package.xmls, colcon build --merge-install, then colcon test --packages-select cobot_detector so a detector-core regression fails the image. runtime (ros:humble-ros-core) copies only /ws/install, sets RMW_IMPLEMENTATION=rmw_cyclonedds_cpp and runs ros2 launch cobot_bringup robot.launch.py.

docker-compose.yaml: one service cobot-ros, restart: unless-stopped, publishes 8000:8000 only.

./runtime_models→ /ws/runtime_models — models.yaml + .onnx (never baked into the image)
./vision_workspace→ /ws/vision_workspace — intrinsics JSON, captures, results
./ros2_ws/src/cobot_bringup/config→ /ws/install/share/cobot_bringup/config — live-editable params, setup, trajectories, calibration

Configuration files

Health & readiness chain

node heartbeats → health_monitor summary → task_manager SystemState capability → WorkflowInfo.ready → UI button enabled. If a button is greyed out, /task/system_state's see_blockers / move_blockers say why.

10. Gotchas for newcomers

  • The arm can move at boot. task_manager.auto_calibrate_on_startup: true runs the startup calibration grid as soon as the robot is ready. Disable it if unattended motion is unsafe in your cell.
  • Calibration lives in two places by design: task_manager sequences the poses (calibration_* params), localization_node does the math (marker_offset_mm, fitters, rms gate). marker_offset_mm (dot vs TCP) and tools.*.tip_offset_mm (suction tip vs TCP) both hang off the same TCP — measure them separately.
  • Manual dot selection is temporary. manual_dot_selection: true because the red_dot ONNX model has not been exported yet; the UI asks you to click the marker on each calibration pose. Keep calibration_sample_timeout_sec > manual_click_timeout_sec.
  • Only cobot_control talks YMConnect. Need a new robot capability? Add a service/action there and consume it from Python; never open a second connection.
  • Pixel vs robot messages are separate types on purpose. ObbDetection has no millimetres; Target has no pixels (only detection_index back-references).
  • Streamer changes: keep the <BIHHBI header and depth aligned to color; the node tolerates framing changes but not header or unit changes.
  • YAML typing: list parameters must be all floats (500.0, not 500) or rclpy declares an integer array and the node refuses to start.
  • Running outside Docker needs cobot_setup.yaml and calibration.yaml reachable — cobot_bringup/setup.py installs only cobot_params.yaml and trajectories.json; compose's bind mount supplies the rest.
  • motoman_cpp is retired (COLCON_IGNORE); the old pybind route is history only. legacy/ and the root CMakeLists.txt are reference material, not part of the build.
